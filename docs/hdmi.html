01

它是什么，为什么需要它

What & Why

一句话：HDMI 是把 DVI 的 TMDS 物理层拿来，再加上音频回传、消费电子控制和内容保护的消费显示接口——电视柜里那根线，本质上是一台跑 8b/10b 编码的实时像素泵。

1999 年 DDI 工作组推出 DVI：3 对数据差分 + 1 对时钟，TMDS 编码，单链 165 MHz。 2002 年家电厂们（Hitachi / Panasonic / Philips / Silicon Image / Sony / Thomson / Toshiba）在 DVI 物理层之上 封装出 HDMI 1.0：同样的 TMDS 流，但消隐期里塞进了 8 声道音频，DDC 上跑 EDID，还预埋了 HDCP 内容保护。 被动 DVI↔HDMI 转接头至今可用，就是因为两者在 TMDS 层完全同构。

它统治的场景全是「整机对整机」：电视、机顶盒、游戏机、投影仪、显示器、soundbar。 这和板级显示接口是两个世界—— RGB 并口是 SoC 直接驱屏的并行总线（几十根线，厘米级）， LVDS把它串化成低压差分降低 EMI， MIPI DSI再用低功耗差分 + 包协议服务手机屏幕； 而 HDMI 面对的是两三米的屏蔽线、随时热插拔、还有版权方的加密要求—— 差分对、HPD 热插拔检测、HDCP 握手都为此而生。

演进主线就是带宽追赶分辨率：1.0→1.2 165 MHz（4.95 Gbps）， 1.3→1.4 340 MHz（10.2 Gbps，上 4K30）， 2.0 600 MHz（18 Gbps，4K60 4:4:4）， 2.1 干脆放弃 TMDS 改用 FRL 固定速率链路（48 Gbps，8K/4K120）。 同期 VESA 的 DisplayPort 走了另一条路：微包化协议，06 节细讲。

FACT / A

血统：DVI 的 TMDS 心脏

Transition Minimized Differential Signaling：8bit 像素编成 10bit 直流平衡码字，3 通道 + 1 时钟共 4 对差分。HDMI 1.0–2.1a 的视频层至今没有离开这套编码（2.1 的 FRL 才换）。

FACT / B

一根缆三种流量 时间复用

有效期传像素，消隐期传控制码，数据岛里塞音频包和辅助数据——04 节会看到一行 2200 拍是怎么被切成这三类航道的。

FACT / C

一切协商从 EDID 开始

sink 在 DDC（就是 I²C，地址 0x50）上暴露 256 字节 EDID：支持哪些分辨率、音频能力、HDCP 版本。读错 EDID，后面全错。

FACT / D

内容保护 HDCP

1.x 在 DDC 上做对称密钥挑战应答；2.x 换成 RSA 协商 + 会话密钥 + 邻近性检查。链路上每台设备都要过——功放是最短的那块板。

02

物理层 · 四对差分与 19 根引脚

Physical Layer

TMDS 主链路只有 4 对差分：3 对数据（R/G/B 各一个通道）+ 1 对时钟；剩下的引脚全是「配角」—— 但黑屏故障有一半出在配角身上：DDC、HPD、CEC、ARC、+5V。下面四张卡片里都是实时运行的波形。

TMDS Data 0/1/23 对差分 · R/G/B 通道PIN 1-9

每个通道每像素时钟发 一个 10-bit 码字（8b/10b 编码后），比特率是时钟的 10 倍。电流模式驱动、终端 50Ω 上拉到 3.3V、摆幅约 ±500mV，TX+/TX− 互补（上图实线=TX+，暗线=TX−）。接收端用时钟对做 PLL 倍频恢复位时钟：

148.5 MHz 时钟 ⇒ 每通道 1.485 Gbps ⇒ ×3 = 4.455 Gbps

HPD：sink 拉高 ≥2ms 表示「在线，来读 EDID」，拔线即落下——热插拔的总闸门。CEC：单线开漏 3.3V、位周期 2.4ms（约 417bps），一只遥控器开关整套影音设备。ARC：把电视的音频沿 pin 13 送回功放；eARC 升级为差分、约 37Mbps。

03

核心交互一 · TMDS 8b/10b 编码流水线

Encoding Lab

为什么 8bit 要变 10bit？两个目的：跳变最少（EMI 小、好恢复时钟）与 0/1 平衡（线上不积累直流偏移）。 下面这个流水线把一个像素字节逐级编出去：8bit 输入 → 9bit 过渡编码 → 10bit 直流平衡。 切换数据序列，观察下方「累积 DC 偏移」图里未编码直传与TMDS 编码的差别。

上传到线上的串行码字：TX+（绿）与 TX−（琥珀）互补，LSB（q0）先行，每位宽度 = TMDS 时钟 ÷ 10。 接收端比较两根线的电压差，而不是绝对电平——这是差分抗共模噪声的根基。
为什么 0/1 平衡能抗干扰：接收端判决门限在中间，若线上 1 长期多于 0，差分电压的「重心」漂移，眼图上下不对称直至误码（红色曲线）； TMDS 用逐码字的取反选择让失衡方向交替抵消，长期偏移被钳在小范围内（绿色曲线；红场这种极端数据直传时会一路漂移）。

8bit 先经 XOR/XNOR 链编成 9bit（跳变最少），再按 0/1 平衡决定是否取反并加上标志位，得到 10bit 码字。 代价是 25% 带宽开销（10/8），换来的是：无需独立参考地、长线直流稳定、EMI 频谱分散—— 这也是 HDMI 线能拉到数米而 RGB 并口只能走厘米级的原因之一。

保护带是 1011001100（视频）与 0100110011（数据岛）这样的固定码——它们在 8b/10b 编码空间里永远不会被像素数据误生成， 接收端靠它们无歧义地切换解码器模式。前导（preamble）则提前 8 拍用 CTL 位预告「下一秒换航道」， 给 PLL 和 FIFO 留出重配置时间。所以拔掉 DE/HSYNC 物理线，HDMI 照样知道画面从哪开始——全在码字里。

带宽计算器 · 4K60 到底要什么档

Bandwidth Math

TMDS 的账很好算：像素时钟 × 色深系数 ÷ 色度因子 = 字符时钟，三道坎 165 / 340 / 600 MHz 决定你要哪一代线材。 切换色度抽样，看 4K60 如何从 594MHz 掉回 297MHz——这就是电视厂商标「4K@60Hz」时常干的 4:2:0 把戏。

HDCP 1.x对称密钥挑战

源经 DDC 读 sink 的密钥选择向量，发一个 64-bit 伪随机数挑战，双方各自算出相同密钥流即认证通过，视频逐符号异或加扰；约每 2 秒轮换、每 128 帧校验。弱点：2010 年主密钥泄露，形同虚设。

HDCP 2.x会话密钥协商

RSA/椭圆曲线身份认证 + AES 会话密钥 + 邻近性检查（往返延时证明设备就在隔壁，防远程转发），支持中继拓扑逐级加密。4K 商业内容普遍要求 2.2——链上任何一台设备不支持，整条链降到 1080p 或黑屏。

06

DisplayPort · 微包、MST 与 USB-C

DisplayPort & MST

DP 把 HDMI 的「固定速率 TMDS 流」换成微包化链路层：视频切成 32–64 字节传输包，加上流 ID 与帧符号， 在 1/2/4 条 lane 上交织。收益是 MST 菊花链——一个 DP 口带一串显示器。点「下一步」看链路建立全过程。

DP 1.3/1.4 用 HBR3；DP 2.0 换 128b/132b 编码（UHBR 10/13.5/20G，有效率 ~97%）。8b/10b 时代 20% 开销与 TMDS 相同。

USB-CDP Alt Mode

USB-C 的 4 对高速差分可整体复用为 DP lane（SST 4-lane，或 2+2 与 USB3 共存），由 CC 线上的 Enter Mode 消息协商——这是「一根线投屏」的物理基础。HDMI 原生的 USB-C Alt Mode 已于 2020 年废弃，如今 Type-C 转 HDMI 都是 USB-C 上的 DP Alt Mode + 协议转换芯片。

对照HDMI vs DisplayPort

传输模型：TMDS 固定流（按像素时钟硬跑） vs 微包链路层（带宽可统计复用）；
通道：3+1 固定 vs 1/2/4 可协商；
多屏：一口一屏（要分配器） vs MST 原生菊花链；
带宽：48G（FRL） vs 32.4G（HBR3）/ 80G（DP2.x UHBR20）；
授权：HDMI 管理局 + HDCP 授权费 vs VESA 免版税；
生态：电视/机顶盒/游戏机 vs PC/显示器/工作站；
热插拔：HPD+DDC（I²C） vs HPD+AUX 通道（1MHz 双线，还能读 DPCD 状态）。

Linux 实战 · drm/kms 视角

Linux Cheat Sheet

HDMI 在 Linux 里属于 DRM/KMS 子系统：card0 之下，每个连接器（HDMI-A-1）是一条 connector → encoder → CRTC → 显示流水线。EDID、模式列表、热插拔事件全部暴露在 sysfs——不需要装任何工具就能查个底朝天。点击任意命令行即可复制。

sysfs — 连接器状态
$ ls /sys/class/drm/ # 每个 connector 一个目录
card0-HDMI-A-1 card0-eDP-1 card0-DisplayPort-1
$ cat .../card0-HDMI-A-1/status
connected # disconnected = HPD 都没起来
$ cat .../card0-HDMI-A-1/enabled
enabled # connected 但没点亮的典型：无匹配 mode
edid-decode — sink 能力
$ cat .../edid | edid-decode | head -30
Manufacturer: DEL Model: U2422 Serial: 12345
DTD 1: 3840x2160 60.000 Hz
CTA-861: VIC 97 3840x2160@60 ... 16:9
HDMI 2.0: SCDC present: yes · Max TMDS: 600MHz
# EDID 是协商的起点：读不到 → 立即回 08 节第 2 步
xrandr — 模式与强制输出
$ xrandr --query | grep -A3 'HDMI'
HDMI-1 connected 1920x1080+0+0 (normal left inverted right)
3840x2160 60.00 + 30.00 # + = EDID 首选
$ xrandr --output HDMI-1 --mode 3840x2160 --rate 60
# EDID 里没有的模式：--addmode + --mode 强推（黑屏三查第 3 步）
$ xrandr --output HDMI-1 --auto # 回到自动首选
dmesg — 插拔与协商日志
$ dmesg -wH | grep -iE 'drm|hdmi|hdcp'
[drm] HDMI-A-1: EDID block 0 valid, ext blocks 1
[drm] HDMI-A-1: video mode 3840x2160@60, clock 594MHz
i915: HDCP2.2 port enabled ... authenticated
# hpd: disable/enable 轮询刷屏 = 接触不良或线太差（08 节）
KMS — card/connector/crtc 对象模型 + modetest
/* DRM 把显示抽象成四类对象，一切从 card 设备出发：card → connector（HDMI 口）→ encoder → CRTC（扫描时序引擎）→ plane（图层）*/
$ ls /dev/dri/ # card0 renderD128
$ cat /sys/kernel/debug/dri/0/HDMI-A-1/force # 强制 connected（测无 EDID 输出）
$ modetest -c -d # libdrm 自带：列 connector/crtc/mode，还能测试画面
$ modetest -M i915 -s 32@31:3840x2160@RG24 # 绕过窗口系统直接点亮
$ libinput list-devices | grep -A2 CEC # cec-usb / /dev/cec0 生态
$ udevadm monitor --kernel --subsystem-match=drm # 看热插拔事件风暴
嵌入式角度：SoC 的 HDMI TX 驱动（如 dw_hdmi / it66121 / lt8618）在设备树里声明，热插拔靠 HPD 中断 + drm_helper_hpd_irq_event() 走完整流程： HPD↑ → DDC 读 EDID → drm_edid 解析 → 填充 connector 的 mode 列表 → 用户态 xrandr/Weston 看到「connected」。 树莓派（vc4-kms-v3d + dw_hdmi）是最低成本的 HDMI 收发实验台，配 edid-decode 和 modetest 足够把 08 节的黑屏三查全部演练一遍。

connected 且 enabled 却无图：edid-decode 看扩展块里的 4K VIC 与 Max TMDS 是否被虚标（廉价显示器重灾区）；把 xrandr 锁到 1080p60 能亮 = 带宽/时序问题，回 05 节算账。

雪花
闪烁
线太长 · 信号完整性

档位越高越挑线：4K60（594MHz）超过 3m 普通线就危险。症状是偶发雪花后恢复、或 dmesg 里 hpd 风暴。解法：Premium/48G 认证短线，或上有源光缆（AOC）——光纤传 TMDS，10–50m 都稳。

只有
1080p
协商降级 · 4:2:0 / 带宽不够

源认为链路只能跑低速：查 EDID 的 Max TMDS Clock、线材认证等级（Standard↔Premium↔48G 三档），以及源端「颜色格式」设置是否锁在 8bpc 4:2:0。电视标「4K60」常默认 4:2:0——05 节算过它只要 297MHz。

2.1 跑
不了 FRL
HDMI 2.1 ≠ 48G · SCDC 未协商

2.1 是「可选特性集」：厂商可以只给 eARC/VRR 不给 FRL。真 FRL 需要源与 sink 都支持 + 线是 Ultra High Speed（48G） 认证 + SCDC 寄存器协商成功（dmesg | grep -i frl 能看到训练日志）。三者缺一，设备默默回落 TMDS 18G。

有图
没声
数据岛 / 声道声明问题

视频走有效期、音频走数据岛——图有声无说明 TMDS 主链路 OK。查 EDID CTA 块的音频能力（采样率/声道）、alsamixer 是否选对输出（aplay -l 找 HDMI），以及功放是否要求 eARC（老 ARC 只有 SPDIF 质量）。

颜色
发灰
RGB 有限/全范围不匹配

画面像蒙了层雾或黑位发灰：xrandr --output HDMI-1 --set 'Broadcast RGB' 'Full'（Intel）对齐两端。HDMI 传统上默认 16–235（limited），PC 显示器期待 0–255（full），驱动猜错就发灰。

CEC
失灵
拓扑里有设备不吃 CEC

CEC 是单线广播总线，任何一台设备死机都能拖垮全网。排查法：逐台断电定位；Linux 侧 cec-ctl --monitor 看总线报文。注意 ARC 与 CEC 共地（pin 17），ARC 接错口会干扰 CEC。

六条铁律GOLDEN RULES

  • 1TMDS 时钟 = 像素时钟，线上比特率恒为它的 10 倍（深色 ×1.25/1.5/2，4:2:0 ÷2）
  • 2一切协商从 EDID 开始：DDC 读不到，源只能猜（通常猜最低档）——见 I²C 页
  • 3HPD 是热插拔的闸门：5V 先上、HPD 再拉高 ≥2ms，源才重读 EDID
  • 4算带宽先算字符时钟：165/340/600MHz 三道坎过不去，画质选项逐个砍（深色→4:2:0→分辨率）
  • 5HDMI 2.1 不等于 48G：FRL 要源、sink、48G 认证线、SCDC 协商四者齐备
  • 6对比板级接口：RGB/LVDS/DSI 是驱裸屏，HDMI/DP 是整机互联——热插拔与内容保护是分水岭

术语表GLOSSARY

TMDS
Transition Minimized Differential Signaling，最小化跳变差分信号：8b/10b 编码 + 电流模式差分对，DVI/HDMI 1.0–2.0 的物理层
DDC · EDID
显示数据通道（就是 I²C）与扩展显示识别数据：sink 自报家门的能力表，256B 起步
HPD
热插拔检测线：sink 拉高表示在线并触发源重读 EDID
CEC
消费电子控制：单线 417bps 广播总线，一只遥控器控制整条电视柜
ARC / eARC
音频回传通道：把电视端音频送回功放；eARC 用差分对、约 37Mbps，承载高清多声道
FRL
Fixed Rate Link：HDMI 2.1 的新链路层，4 lane × 最高 12G，16b/18b 编码，取代 TMDS
SCDC
Status and Control Data Channel：HDMI 2.1 起挂在 DDC 上的状态寄存器组，FRL 训练的协商现场
DSC
Display Stream Compression：视觉无损流压缩（约 3:1），8K/4K120 的入场券
HDCP
High-bandwidth Digital Content Protection：内容保护，1.x 对称密钥 / 2.x RSA 会话加密
AUX CH · DPCD
DP 的 1MHz 双线辅助通道与它的寄存器组：链路训练、EDID 读取、流分配全靠它
SST / MST
单流 / 多流传输：MST 让一个 DP 口经菊花链带多台显示器，每个流有独立时序
Alt Mode
USB-C 高速差分对外借给其他协议：DP Alt Mode 可复用全部 4 lane（SST）或 2+2 共存
